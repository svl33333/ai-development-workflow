# Issue #4 正式仕様書
- Status: adopted
- Owner: svl33333
- Date: 2026-09-05
- Related issue: https://github.com/svl33333/ai-development-workflow/issues/4
- Scope: 個人環境のCodex導入フロー、および正式Issue・仕様変更のガード

## 1. 問題と目的

現在の導入処理は共通マスターをローカル絶対パスで指定するため、別PCで同じ導入結果を再現するにはclone先の調整が必要である。また、正式仕様のGrillingと人間承認が完了する前に、正式なGitHub Issueが作成される経路がある。

本仕様は、GitHub上の共通マスターを導入の正式な取得元にし、取得したバージョンを固定・記録する。同時に、仕様確定前および開発中の未承認変更が、GitHub Issue、実装、コミットへ混入しないよう、状態ファイルとCLIによるfail-closedなガードを定義する。

## 2. アクターと責務

| アクター | 責務 |
| --- | --- |
| ユーザー | 仕様承認、Grillingスキップの明示、最終公開承認、ChatGPT Project作成、認証やマージなど人間操作 |
| Codex | リポジトリ確認、検討記録、CLI実行、導入、Issue操作、実装、テスト、失敗時の停止と再開案内 |
| ChatGPT | 設計、実装計画、計画レビュー、PRレビュー |
| GitHub | 共通マスターの取得元、Issue・履歴・ラベルの保管先 |

導入Skillは初期導入を担い、正式Issue作成ガードは状態ファイルとCLIを担う。導入Skill単体でIssue作成許可を判定しない。

## 3. 範囲

### 対象

- GitHub URLを起点とする共通マスターの取得・検証・導入
- 取得コミットまたはバージョンの固定と記録
- 既存ファイルを保護した導入と競合報告
- 正式Issueの作成・更新前の承認ガード
- Issue #4内の「初期導入Skill改善」と「Issue作成ガード」の2テーマ
- 正式Issue完成後の開発中の仕様変更管理

### 対象外

- ChatGPT Projectの完全自動作成
- GitHub認証情報のリポジトリ内保存
- 個人環境と会社環境の自動同期
- 仕様承認前の正式Issue作成・更新
- 承認対象と異なるIssue内容の公開
- 既存ファイルの無断上書き

## 4. 要件

### 4.1 GitHub起点の初期導入

#### REQ-4A-001（must）取得元

導入処理は、GitHubリポジトリURLを共通マスターの正式な取得元として受け付ける。PC固有の共通マスター絶対パスを必須入力にしてはならない。

#### REQ-4A-002（must）バージョン固定

導入処理は、ブランチ、タグ、またはコミットを解決し、実際に取得したコミットIDまたは同等の一意なバージョンを記録する。同一コミットを指定した導入結果は、同一の管理対象ファイル集合と内容になる。

#### REQ-4A-003（must）導入範囲

Skills、プロンプト、テンプレート、ワークフロー定義、必要なスキーマをGitHubから取得し、対象プロジェクトの`.ai-workflow/`等の規定位置へ導入する。

#### REQ-4A-004（must）既存ファイル保護

対象プロジェクトに同じ相対パスのファイルが存在する場合、無断で上書きせず、競合ファイルと更新候補として報告する。

#### REQ-4A-005（must）失敗時の停止

取得、認証、検証、コピー、導入後検証のいずれかが失敗した場合、導入成功として記録してはならない。現在工程、失敗理由、再開に必要な操作を表示する。

#### REQ-4A-006（must）導入証跡

対象プロジェクトに、取得元URL、取得コミットまたはバージョン、導入時刻、追加ファイル、競合ファイル、検証結果、未完了の人間操作を記録する。

#### REQ-4A-007（must）人間操作境界

ChatGPT Project作成、資格情報登録、PR公開、マージは人間操作または人間承認の境界を維持する。導入処理は必要な操作を表示して停止し、完了後に再開できる。

### 4.2 正式Issue作成ガード

#### REQ-4B-001（must）許可条件

正式Issueの新規作成、暫定Issueの正式化、既存正式Issueの更新は、対象テーマごとに次の条件をすべて満たす場合だけ許可する。

1. Grillingが完了している、またはGrillingスキップが明示確認済みである
2. ユーザーが対象仕様を明示承認している
3. 仕様記録、仕様ID、仕様版が存在する
4. 仕様とIssue内容の対応関係を検証できる
5. 公開直前の対象Issue、タイトル、本文、ラベル、リンク、操作内容をユーザーが最終承認している

#### REQ-4B-002（must）未承認時のfail-closed

許可条件が不足・不整合の場合、GitHub APIを呼び出してはならない。CLIは現在工程、不足条件、次に実行すべき操作を表示して停止する。

#### REQ-4B-003（must）Grillingスキップ

自然言語でスキップが指示された場合、CLIは一度だけ次の意味を確認する。

> Grillingをスキップし、未実施のまま正式Issue作成へ進みます。仕様承認・記録・対応確認は別途必須です。

確認後のスキップ記録には、理由、指示者、日時、残存リスクを含める。スキップはGrilling完了だけを免除し、仕様承認、仕様記録、対応確認、最終公開承認を免除しない。

#### REQ-4B-004（must）状態と証跡

機械判定用の状態ファイルは`.codex/workflow-state.json`とする。テーマごとに一意な仕様IDと版を持たせ、Grilling記録、スキップ記録、承認記録、Issue本文ハッシュ、公開結果を紐付ける。CLIだけが状態遷移を書き込む。

承認記録には、仕様ID、承認者、承認日時、承認対象の版またはハッシュ、承認文言を含める。状態データの整合性を検証し、不整合や改ざんを検出した場合は再承認を要求する。

#### REQ-4B-005（must）状態遷移

基本状態を次の通りとする。

```text
draft
  -> grilling
  -> grilling_complete | grilling_skipped
  -> spec_approved
  -> ready_to_publish
  -> published
```

公開操作の失敗は`publish_failed`または`label_sync_failed`とし、試行日時、エラー、外部Issueの確認結果を記録する。

#### REQ-4B-006（must）暫定メモ

暫定メモは`docs/pending-issues/<識別子>.md`に1テーマ1ファイルで保存する。正式Issue本文には暫定草案や暫定メモへのリンクを残さない。検討履歴はリポジトリとGit履歴で保持する。

#### REQ-4B-007（must）Issue #4の構造

Issue #4は次の2セクションを持つ。

- 初期導入Skill改善
- Issue作成ガード

各セクションは目的、仕様、実装範囲、受入条件を独立して記述する。

#### REQ-4B-008（must）明示CLI操作

状態遷移と公開操作を分離した明示操作を提供する。最低限、`prepare`、`approve`、`skip-grilling`、`publish`、`retry`に相当する操作を定義する。汎用GitHub APIラッパーによるガード外のIssue操作は提供しない。

#### REQ-4B-009（must）既存Issue更新

既存Issue更新時は、リポジトリ、Issue番号、現在のタイトル、更新前本文ハッシュを検証する。外部変更が検出された場合は更新を拒否し、最新状態の再取得と再承認を要求する。

#### REQ-4B-010（must）公開と冪等性

公開後は公開Issue番号と公開本文ハッシュを記録し、同じ仕様の重複作成を拒否する。ラベルは状態ファイルから導出する表示情報として同期し、不一致を完了扱いにしない。

## 5. 開発中の仕様変更

### 5.1 分類

変更を次の4分類で記録する。

- `bug_fix`: 承認済み仕様どおりに戻す修正
- `clarification`: 既存仕様の意味を変えない明確化
- `scope_change`: 目的または機能範囲の変更
- `constraint_change`: 外部契約、データ形式、セキュリティ境界などの制約変更

### 5.2 継続と停止

`bug_fix`と`clarification`は、既存の受入条件、公開API、データ形式、セキュリティ境界、スコープを変えない場合に限り、Codexの判断で継続できる。分類、理由、影響範囲、判断根拠を実装前または直後に記録し、人間の事後確認を受ける。

`scope_change`と`constraint_change`は実装を停止し、ユーザー確認を取る。承認待ち中は変更案の整理、影響調査、既存テスト確認、計画差分作成まで進められるが、仕様依存の実装、Issue更新、コミットは停止する。

### 5.3 承認、成果物、Issue

変更申請メモに分類、理由、影響範囲、対象仕様版を記録する。大きな変更は再Grillingと人間の仕様承認を行う。承認後、計画、レビュー結果、テスト、実装を「維持」「更新」「無効化」に分類し、無効化した成果物は再作成する。

軽微な変更は既存Issueの仕様版を更新し、大きな変更は新規Issueとして追跡する。新規Issueには元Issueとの親子関係、仕様ID、版、依存関係、引継ぎ範囲、完了条件を記録する。元Issueと新Issueは独立した完了条件を持つ。

変更が却下された場合は却下理由を記録し、未採用の実装・計画差分を破棄または分離して元の承認済み仕様へ復帰する。

### 5.4 緊急変更

緊急変更ではGrillingをスキップできるが、人間の明示承認、変更理由、影響範囲、暫定対応の記録を必須とする。通常業務へ戻る前に事後Grillingまたはレビューを完了する。恒久化する場合は正式な新仕様版へ取り込む。

### 5.5 再テスト

変更後は、無効化・更新対象のテスト、回帰リスクのある既存テスト、新しい受入条件を実行する。変更の影響評価と再テスト範囲を記録する。

## 6. アーキテクチャとデータフロー

```text
GitHub共通マスター
  -> 取得・コミット固定
  -> 構造検証
  -> 対象プロジェクトへ非破壊導入
  -> .ai-workflow/導入証跡

仕様メモ / Grilling記録
  -> テーマ別仕様ID・版
  -> 人間承認
  -> 状態ファイル検証
  -> 公開直前差分表示
  -> 人間最終承認
  -> GitHub Issue作成・更新
```

信頼境界は、ローカルの仕様・状態、対象プロジェクト、GitHub外部状態、会社環境に分かれる。会社環境の詳細テスト結果、ログ、固有ポリシーは個人環境へ自動送信しない。

## 7. エラー、競合、再試行

- 取得不能、認証待ち、検証失敗: 成功状態へ遷移せず、停止理由と再開操作を表示する
- 状態ファイル不整合: 状態を無効として再承認を要求する
- Issue本文ハッシュ不一致: 外部変更として拒否し、再取得・再承認する
- 本文成功・ラベル失敗: `label_sync_failed`として完了扱いにしない
- API結果不明: 公開済みか外部状態を確認してから再試行する
- 同じ仕様の再公開: 公開済み記録を検出して重複作成を拒否する
- 子Issue作成: 仕様ID、版、対象範囲を検証し、対象外の自動処理から除外する

## 8. セキュリティと権限

- GitHub認証情報をリポジトリへ保存しない
- 読み取り・取得と外部Issue書き込みを分離する
- Issue書き込みは状態検証と最終承認を通過したCodex操作だけに限定する
- 破壊的操作、マージ、資格情報登録、会社固有ポリシー変更は人間承認を必要とする
- 不確実な外部状態を成功とみなさない

## 9. 受入テスト計画

### 導入

- ローカル絶対パスなしのGitHub URL導入
- 同一コミットの別PC再現
- 競合ファイルの非上書きと報告
- 取得失敗、認証待ち、導入後検証失敗からの停止・再開
- 導入元、コミット、時刻、結果の証跡

### Issueガード

- 未承認時のAPI未呼び出し
- Grilling完了後の許可
- Grillingスキップと1回の念押し確認
- 仕様承認・記録・対応確認の不足
- 状態ファイル改ざん・不整合
- 仕様版または本文ハッシュ不一致
- 対象Issue取り違え・同時編集
- 本文更新とラベル更新の部分失敗
- API失敗後の外部状態確認と再試行
- 公開済み仕様の重複作成拒否
- Codexの最終承認後だけの成功経路

### 仕様変更

- `bug_fix`／`clarification`の継続条件
- `scope_change`／`constraint_change`の停止と再承認
- 変更却下後の元仕様復帰
- 計画・レビュー・テスト・実装の維持／更新／無効化判定
- 親Issue・子Issueの重複処理防止
- 緊急変更の記録・事後レビュー・恒久仕様化
- 影響評価に基づく再テスト

## 10. 決定事項とリスク

### 決定事項

- Issue #4は既存Issueを維持し、正式仕様本文へ置き換える
- Issue本文は最終仕様だけを残し、暫定メモへのリンクは残さない
- 導入SkillとIssue作成ガードは別責務として扱う
- Issue #4本文では2テーマを別セクションとして管理する
- CodexがGitHub操作を実行し、ユーザーが最終承認する
- Grillingスキップは可能だが、仕様承認・記録・最終承認を免除しない

### リスクと対応

| リスク | 対応 |
| --- | --- |
| Codex実行環境ごとのGitHub認証差 | 認証待ちを明示状態にし、資格情報を保存しない |
| 状態ファイルの手動改変 | 整合性ハッシュと再承認で検知する |
| Issueの同時編集 | 更新前本文ハッシュで拒否する |
| 新規Issueの自動処理重複 | 仕様ID・版・対象範囲を検証する |
| 暫定対応の恒久化漏れ | 事後レビューと正式仕様版への取り込みを必須にする |
| GitHub API部分成功 | 外部状態を確認してから再試行する |

## 11. 実装フェーズ

1. GitHub取得元、コミット固定、導入証跡、非破壊コピーを実装する
2. 導入後検証、認証待ち、失敗時再開、別PC再現テストを実装する
3. `.codex/workflow-state.json`、テーマ別仕様ID・版、承認証跡を実装する
4. `prepare`、`approve`、`skip-grilling`、`publish`、`retry`とfail-closed判定を実装する
5. GitHub Issueの新規作成・更新、ハッシュ検証、ラベル同期、冪等性を実装する
6. 仕様変更分類、影響評価、再承認、親子Issue、緊急変更を実装する
7. 受入テスト、Codexアダプター、Copilotアダプター、別PCの導入スモークを完了する

## 12. 完了条件

- PC固有の共通マスター絶対パスなしにGitHub起点で導入できる
- 同一コミット指定で別PCに同一結果を再現できる
- 導入結果・取得元・バージョン・競合・検証結果を記録できる
- 仕様承認前の正式Issue作成・更新をAPI呼び出し前に拒否できる
- 承認済み仕様とIssue内容の対応、冪等性、同時編集、部分失敗、再試行を検証できる
- 開発中の仕様変更を分類し、停止・承認・再テスト・履歴更新を一貫して扱える
- CodexとCopilotの各アダプターで受入テストが通る

## 13. 引継ぎ点

本仕様はGrillingと人間の共有理解確認を完了した正式仕様である。次の工程は、実装前の独立レビュー、実装計画、実装、テスト、PRレビューである。実装開始は本仕様の範囲内に限定し、仕様変更は本仕様の変更管理手順を通す。
