## 目的

Codex with ChatGPT を利用する開発ワークフローで、Codex側からChatGPT Project内の会話を安全に開始・再開・送信・待機・取得できる会話操作アダプターを整備する。Codexが実装・Git操作を担い、ChatGPTは計画・レビューを担う責務分離を維持する。

## 背景

現在は、Project作成後の会話操作や応答待ち、途中再開、GitHub認証の復旧に手動作業が残っている。特に、ChatGPTの推論中をタイムアウトと誤認したり、再試行時に同じ指示を二重送信したりする問題を防ぐ必要がある。

## 方針

- ChatGPT Projectは原則として人間が手動作成する
- Codexは作成を促すProject名を自動生成する
- Project名は「基本名称--8文字の英数字ID」とする
- ユーザーが作成完了を伝えた後、CodexがProject情報を照合する
- Project一覧・メタデータを取得できない場合のみ、Project URLの入力を求める
- 一致しないProjectへ推測で接続しない
- ChatGPT側はOAuthコネクター、Codex側のGitHub操作はfine-grained PATを利用する
- Project自動作成、GitHub App、複数ワークスペース横断管理、統合ダッシュボードは別Issueとする

## 実装要件

### 実装計画の品質ゲート

- 実装計画を作るChatGPT会話と、実装計画をレビューする工程専用のChatGPT会話は必ず分離する
- 計画レビューは、工程専用の同一レビュー会話を最低3ラウンド継続利用する。各ラウンドで、その会話自身の過去の指摘・採否記録を照合し、前回指摘の修正状況を確認する
- 実装計画レビュー、PRレビュー、プロトタイプ評価など、工程が異なるレビューにはそれぞれ別の専用会話を使う
- 重大な設計判断、未解決のCritical／High、または人間が要求した場合だけ、別の新規会話によるセカンドオピニオンを追加できる。これは工程専用レビュー会話を置き換えない
- 第1・第2ラウンドで重大な問題が見つからなくても早期終了しない
- 各ラウンドで、指摘ごとの採否・根拠・計画への反映内容、または変更不要と判断した根拠を保存する
- 3回完了後もCritical／High相当の未解決指摘がある場合は、改善・再レビューを継続するか人間判断へ停止する
- `plan_review_iteration < 3` の間は実装計画の人間承認および実装フェーズへの遷移を拒否する

### 会話操作アダプター

以下の操作をワークフロー本体から分離したインターフェースとして提供する。

- `startConversation`
- `resumeConversation`
- `sendMessage`
- `waitForResponse`
- `readResponse`
- `getStatus`

非同期処理を前提とし、送信・待機・取得を個別に再試行できるようにする。

### 状態管理

基本状態を次のように管理する。

`INIT → PLAN → EXECUTING → EXECUTED → REVIEW → DONE/BLOCKED`

保存対象には、少なくとも以下を含める。

- タスクID
- 反復回数
- Project識別情報
- 会話識別情報
- 会話の役割（計画作成／工程専用レビュー／セカンドオピニオン）と工程名
- 計画作成会話と工程専用レビュー会話の対応関係、およびレビュー会話の交代履歴
- 対象ワークスペース
- 現在状態
- 最後に処理したメッセージID
- 次の処理
- 要約された失敗理由

会話URL・Project情報はCodex側のローカルワークスペース設定に保存し、リポジトリへ認証情報を保存しない。
工程専用レビュー会話が利用不能になった場合は、過去のレビュー・採否記録を失わずに停止する。代替会話の開始は人間承認後にだけ行い、交代理由と新旧の会話識別情報を記録する。

### 再試行・再開

- 通信障害は指数バックオフで再試行する
- 送信前にタスクID、反復回数、メッセージIDの送信済み状態を確認する
- タイムアウトしても再送せず、状態を再取得する
- ChatGPTが推論中の場合はタイムアウト扱いにしない
- 仕様変更・権限変更・受入条件変更は自動判断しない
- 軽微な補完は、既存の仕様・Issue・計画から一意に導ける場合だけ許可する
- BLOCKED時は理由と人間の判断事項を提示して停止する

### Project特定

- 基本名称と固有IDが完全一致するProjectのみ候補にする
- 同一IDが複数ある場合は最近使われたProjectを第一候補として提示するが、自動接続せず人間の確認を待つ
- 会話開始後にワークスペース名とリポジトリ識別情報を確認する
- 不一致時は処理を停止する
- ユーザーには期待Project名、検出候補、不足情報、次の操作を表示する

### GitHub認証

- Codex側のPAT作成は、ユーザーのGitHub認証・最終承認を必須とする
- PATは対象リポジトリ限定・最小権限・有効期限付きとする
- PATはOS資格情報ストア等へ登録する
- GitHub操作前に対象リポジトリへの権限と期限を検証する
- 認証エラー時は登録済みの同じPATで1回だけ再試行し、その後はユーザー判断を待つ
- ChatGPT側はOAuthコネクターを使用し、Codex側PATを共有しない
- 操作種別、対象、Issue/PR番号、結果、失敗理由だけを監査記録として残す

## テスト

以下をfixture、統合テスト、実環境E2Eに分けて検証する。

- Project特定
- 会話開始
- 指示送信
- ChatGPT推論中の待機
- 応答取得
- 通信失敗からの再開
- 二重送信防止
- BLOCKEDからの人間承認後の再開
- PATの権限・期限検証
- PATの同一資格情報による1回限りの再試行
- 誤Project・誤ワークスペース接続の防止
- 計画作成会話とレビュー会話の分離、同一工程のレビュー会話の継続利用、工程間のレビュー会話分離
- 中断後に同じ工程専用レビュー会話を再開できること、および承認なしに代替会話へ切り替えないこと

実環境E2Eでは、手動Project作成からCodexによる特定、会話開始、指示送信、応答待機、再開までを確認する。

## 完了条件

- Codex側から既存Project内のChatGPT会話を開始・再開できる
- 状態管理付きで指示送信・応答待機・応答取得ができる
- ChatGPT推論中を誤ってタイムアウト扱いしない
- 失敗時に同じ指示を二重送信せず再開できる
- Project誤接続を防止できる
- Codex側GitHub操作でPATを安全に利用できる
- fixture、統合テスト、実環境E2Eが成功する
- 設定仕様、状態遷移、復旧手順、テスト結果をリポジトリに記録する
- 人間の承認後にのみ実装計画・実装フェーズへ進む
- 最低3回の計画レビューと各ラウンドの改善記録が揃うまで、実装計画を承認・実装開始できない
- 最低3回のレビューが、計画作成会話とは別の同一工程専用レビュー会話で継続していることを検証できる
