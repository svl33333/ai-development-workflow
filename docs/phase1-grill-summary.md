# Phase 1 仕様サマリー

- Status: needs-review
- Scope: 個人環境の Codex + ChatGPT（codex-with-chatgpt / C2C）
- Owner: ユーザー
- Date: 2026-09-04
- Related: [AI開発ワークフローパッケージ仕様書](ai-development-workflow-package-spec.md)

## 1. 問題と目的

AIによる実装速度の向上に伴い、仕様・判断・検証結果の引き継ぎが会話履歴に依存しやすく、プロトタイプから本番実装、レビュー、マージまでの状態を追跡しにくい。

Phase 1では、Codexが実行主体、ChatGPTが設計・レビュー主体となる開発フローを、実際にIssueを解決する実装が完成するところまで一巡させる。

## 2. 役割分担

### Codex

- 対象リポジトリ・既存資料の調査
- ユーザーへのヒアリングとgrill記録の保存
- `concept-brief`、Issue草案、状態、実行記録の作成・更新
- ChatGPTへの依頼と成果物の受領
- コード編集、テスト、修正、コミット
- ローカルPR草案と最終PR本文の作成
- 人間承認後のGitHub PR公開・マージ
- 完了処理、残課題、障害記録の更新

### ChatGPT

- プロトタイプの詳細設計・実装計画
- プロトタイプの評価レビュー
- 本番Issue・grill成果物を入力とした実装計画
- 実装計画の独立レビュー
- Codexが作成したPR草案、差分、テスト結果のPRレビュー
- 指摘ごとの重要度、根拠、影響、推奨対応の提示

ChatGPTはC2CのMCP経由でリポジトリ内資料・Git差分・テスト結果を読み取るが、ファイル編集・シェル実行・コミット・Issue/PR投稿は行わない。会話履歴をProject間で自動継承せず、Codexが構造化成果物を引き継ぐ。

### 人間

仕様確定、本番移行、計画承認、仕様変更、危険操作、PR公開前確認、マージ承認を行う。マージは人間の明示承認後にCodexが実行する。

## 3. Projectと会話

- プロトタイプProjectと本番Projectを分離する。
- 各工程・目的ごとにChatGPT会話を分離する。
- Phase 1ではProject作成・命名・設定の自動化を目標とする。
- 自動作成できない操作は、Codexが設定内容を生成し、ユーザーが一度だけ手動適用するフォールバックを持つ。
- Codexは作業種別、対象Project、入力資料、成果物、完了条件を含む起動情報を生成する。

## 4. フロー

### プロトタイプ

1. Codexがアイデアをヒアリングし、基本コンセプト・ゴールを含む粗い`concept-brief`を作る。
2. ChatGPTが詳細設計、実装計画、評価基準を作る。
3. 人間承認後、Codexが実装・テストする。
4. ChatGPTがMCPで差分・テスト結果・評価記録をレビューする。
5. 結果を`ITERATE`、`PROMOTE_CANDIDATE`、`STOP`に分類する。
6. `ITERATE`ではCodexが指摘をユーザーへ返し、承認後に修正・テスト・再レビューする。
7. `PROMOTE_CANDIDATE`ではCodexが設計・評価結果・失敗条件・残課題を整理し、人間承認後に本番grillingへ進む。

### 本番

1. プロトタイプの成果物を入力としてCodexが本番grill-with-docsを実施する。
2. Codexが`CONTEXT.md`、ADR、Issue草案を整理する。
3. grilling完了後、Codexが本番用GitHub Issueを作成する。
4. ChatGPTがIssueを主入力として実装計画を作る。必要に応じてMCPで現行コード・資料を事実確認するが、Issueにない要件を追加しない。
5. ChatGPTが別会話で実装計画を独立レビューする。
6. 人間が計画を承認する。
7. Codexが実装・テスト・修正を行う。
8. CodexがローカルPR草案を保存し、ChatGPTが差分・テスト結果・計画・Issueをレビューする。
9. Critical／HighはCodexが自動修正・テスト・再レビューする。仕様変更が必要な指摘は停止して人間へ戻す。
10. Codexが最終PR本文を作成し、人間が差分・本文・テスト・未解決指摘・対象ブランチを確認する。
11. 人間の明示承認後、CodexがGitHub PRを公開する。
12. 公開後の追加変更は再レビュー・再承認を必要とする。人間の承認はPR番号と最新コミットに紐づける。
13. Codexが人間承認後にマージし、完了処理を行う。

## 5. PR本文の標準項目

- Issue URL
- このPRで対応する範囲
- このPRで対応しない範囲
- 確認結果（テスト、動作確認、未確認範囲、URL・スクリーンショット）
- 変更点概要
- なぜこの変更が必要か
- 主な変更内容
- レビュアーに重点的に確認してほしい点
- 未解決事項・既知の制約
- 補足情報

Issue本文は転記せず、リンクで参照する。

## 6. 成果物と状態

必須成果物は、`concept-brief`、プロトタイプ設計、評価記録、grill記録、Issue、実装計画、レビュー記録、状態ファイル、残課題とする。ファイル名にはプロダクトID・工程・作業ID・成果物種別・バージョンを含める。

状態はCodexが管理する機械可読ファイルを正本とし、人間向け記録を併記する。最低限、次を持つ。

```yaml
workflow_version: 1
project_id: sample-product
work_id: issue-001
stage: production_pr_review
status: human_waiting
agent: codex
chatgpt_project: production
artifacts: []
base_revision: abc123
current_revision: def456
next_action: human_approve_publish
stop_reason: null
updated_at: 2026-09-04T00:00:00Z
```

エージェント状態には、エージェント種別、担当工程、状態、開始時刻、最終更新、待機理由、次アクション、エラーを含める。同じプロジェクト・工程・作業IDの書き込みにはロックを設ける。

## 7. 停止・復旧

次の場合は状態を保存して停止する。

- 仕様・設計・受入条件の変更が必要
- 安全・機密境界の重大な懸念
- 入力不足、接続障害、テスト不能
- 同一失敗の反復、最大試行回数到達
- ユーザーによる停止
- ブランチ、コミット、バージョン、成果物の不整合

停止後は、未完了工程から再開する。最初からの再実行は明示指定とする。復旧前に入力・バージョン・Git状態・未解決判断を再検証する。

## 8. セキュリティと環境差

個人環境では対象リポジトリ内の参照を許可するが、認証情報・秘密情報・不要な個人情報は除外する。会社環境の詳細ログ、実行履歴、固有ポリシーは会社環境内に留め、個人環境へ自動連携しない。会社環境からのフィードバックはユーザーが機密確認後に手入力する。

## 9. Phase 1の範囲と完了条件

### 実装するもの

- プロトタイプから本番PR完了までの基本フロー
- Codex／ChatGPTの受け渡し契約
- 状態・成果物・レビュー記録
- 承認ゲート、停止、再開、排他制御
- PRレビューと修正・再レビュー
- Codex/C2Cのfixtureと自動テスト

### 後回しにするもの

- 複数プロジェクト横断の進行状況UI
- 高度な自動復旧
- 会社環境対応
- 完全自動のChatGPT Project作成（実現可否の検証はPhase 1に含める）

### 完了条件

小規模でテスト可能なfixtureプロジェクトで、プロトタイプ開始から本番Issue解決、PRレビュー、修正、承認、Codexによるマージ、完了処理までを一巡できること。停止・再開・接続障害・レビュー修正も検証でき、実際にIssueを解決する実装が完成すること。

## 10. 未解決・要検証

- C2C接続障害からの復旧方法

- GitHub CLI/APIの認証・PR公開・マージ制約
- Codexが人間承認を安全に検証する方式
