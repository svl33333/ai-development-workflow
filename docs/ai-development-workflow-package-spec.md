# AI開発ワークフローパッケージ仕様書

- Status: implementation-approved
- Scope: Phase 1は個人環境のCodex + ChatGPT（codex-with-chatgpt / C2C）。会社環境は後続。
- 詳細な合意事項: [Phase 1仕様サマリー](phase1-grill-summary.md)

## 目的

AIによる実装速度向上に伴う理解負債を抑制し、CodexとGitHub Copilotで共通の開発フローを運用するための共通マスターを作成する。

## 基本方針

- 共通マスターは独立したGitHubリポジトリで管理する
- 共通マスターから各環境への配布・更新は一方向とする
- Phase 1ではCodexが実行主体、ChatGPTが設計・レビュー主体となる。Codex/Copilotの共通化は後続のアダプター設計で維持する
- 各プロダクトのオーケストレーターは各環境内で完結する
- GitHub操作は、利用可能な場合は永続OAuthのGitHubコネクターを標準経路とし、CLI再認証はコネクターが利用できない場合だけのフォールバックとする
- プロトタイプProjectと本番Project、各工程のChatGPT会話を分ける
- 仕様確定、本番移行、計画承認、仕様変更、外部公開、マージ、破壊的操作、会社ポリシー変更は人間の承認を必須にする
- 会社環境の詳細テスト結果・ログ・固有ポリシーは環境外へ自動送信しない
- 会社環境からのフィードバックは、ユーザーが機密確認後に手入力する

## フロー

### プロトタイプ

アイデア受付 → 軽量grilling → プロトタイプ作成 → 評価 → 本番移行候補作成 → ユーザー承認 → 本番仕様grilling

Codexが検証結果、利用シナリオ、失敗条件、採用・却下した案、再利用可能な素材、残課題を構造化して保存し、人間承認後に本番grillingへ引き継ぐ。プロトタイプコードの本番昇格は本番移行承認に含める。

### 本番開発

本番grilling → 仕様確定のユーザー承認 → `CONTEXT.md`/ADR更新 → Issue作成 → ChatGPTによる実装計画 → ChatGPTによる独立計画レビュー → ユーザー承認 → Codexによる実装・テスト → ローカルPR草案 → ChatGPTによるPRレビュー → Codexによる修正・再レビュー → ユーザー承認 → CodexによるPR公開・マージ → 知識・残課題更新

## アーキテクチャ

共通マスターには、フロー定義、Skills、プロンプト、テンプレート、状態遷移、成果物スキーマ、検証スクリプト、Codexアダプター、Copilotアダプター、fixtureを含める。ChatGPT側のProject設定は共通マスターの生成物として扱う。

各プロダクトには`.ai-workflow/`を配置し、設定、状態、成果物、実行記録、レビュー記録、残課題を管理する。状態ファイルはMarkdown本文とYAML front matterを組み合わせ、プロダクトID・工程・作業ID・成果物種別・バージョンを記録する。

### モード

- 自動モード：現在工程を判定し、次の承認ポイントまたはブロッカーまで進める
- 手動アシストモード：ユーザーが個別Skillを呼び出す。成果物・状態・承認条件は自動モードと共通にする

## 権限と停止条件

オーケストレーターは調査、成果物作成、コード編集、テスト、レビュー、Issue/PR作成、ユーザー承認後のPR公開・マージを行える。次の操作では必ず停止する。

- 本番仕様の確定
- プロトタイプから本番への移行
- 会社固有ポリシーの変更
- 破壊的操作
- PR公開前の最終確認
- マージ承認
- ルール衝突、前提矛盾、機密境界違反の可能性

## 機密境界

会社環境でのテスト詳細、ログ、実行履歴、会社固有ポリシーは会社環境内に保存する。個人環境との自動連携は行わない。必要な場合は、ユーザーが機密性を確認して抽象化した情報だけをワークフロー改善用に手入力する。

## 操作

- `setup`：プロジェクトを調査して導入・初期設定する
- `status`：工程、承認状態、ブロッカー、残課題を表示する
- `next`：次工程を判定し、承認ポイントまで進める
- `validate`：状態、成果物、リンク、互換性、工程遷移を検証する
- `update`：共通マスター更新候補を確認し、承認後に適用する

## GitHub認証・操作の標準経路

GitHub Issueの取得・更新・クローズ、コメント、リポジトリ情報の取得、API経由のcommitはGitHubコネクターを優先する。コネクターのOAuth認証は環境に保持し、各操作のたびにログインし直さない。Codexはローカルの編集・テスト・commit準備を担当し、GitHubへの反映はコネクターのcommit API、または既存のSSH／Git Credential Manager認証を利用する。

再認証は401など明確な認証失効が確認された場合だけ行う。認証情報をリモートURL、リポジトリ、成果物、ログへ保存しない。コネクターが使えない場合は、操作を黙って省略せず、GitHub CLIの既存認証を確認し、必要なときだけユーザーへ再認証を依頼する。

## 初期版の完了条件

個人環境のCodex + ChatGPTで、fixtureプロジェクト上でprototypeからproduction、Issue解決、PRレビュー、修正、承認、CodexによるPR公開・マージ、validate、セッションを跨いだ再開までの一連のフローを実行できること。停止・接続障害・状態競合・レビュー修正を含む自動テストが通り、実際にIssueを解決する実装が完成すること。

## 未検証事項

- 会社環境から共通マスターを読み取れるか
- 会社内GitHubのホスト・認証・GitHub CLI/API制約
- Copilotのinstructions、prompt、custom agentの利用可否
- 会社端末で利用可能なランタイム
- 会社環境のテスト結果から手動転記できる項目

## E2Eで追加した運用条件

- 状態ファイルの改行コードはLF/CRLFのどちらでも読み取れること。
- `production_pr_draft`以降はプロダクトルートのGit管理を必須とし、実差分なしでPRレビューへ進めないこと。
- Prototype ProjectとProduction Projectの振り分けを工程ごとに検証すること。
- ライブC2Cが利用できない場合は、外部会話を擬似的に自動実行したことにせず、fail-closedしてCodex with ChatGPTの手動フォールバックへ切り替えること。
