# AI開発ワークフローパッケージ仕様書

- Status: draft
- Owner: user
- Date: 2026-09-02
- Scope: 個人環境のCodex、会社環境のVS Code + GitHub Copilot

## 1. 問題と目的

AIによる実装速度の向上に伴い、仕様・設計判断・残課題の理解が追いつかなくなる問題を防ぐ。個人環境と会社環境で同じ開発フロー、成果物形式、承認基準を使える共通マスターを提供し、環境差はアダプターと環境側ポリシーで吸収する。

### Goals

- AIの成果物を、工程・成果物・承認記録として追跡可能にする
- プロトタイプから本番開発へ、検証結果を無駄なく引き継ぐ
- CodexとGitHub Copilotで共通の開発フローを実行できるようにする
- AIが調査・実装・テスト・レビュー・PR作成まで進められるようにする
- 仕様確定、本番移行、マージ、ポリシー変更は人間が承認する
- 会社環境の機密情報を環境外へ自動送信しない

### Non-goals

- AIによる仕様確定や本番移行承認の自動化
- 会社環境のテストログ・詳細結果の個人環境への自動転送
- 特定のAIモデルやベンダーへの依存
- 初期版での外部サーバー・専用データベースの構築

## 2. 用語

- 共通マスター：フロー、Skills、テンプレート、検証ルール、アダプターを管理する独立GitHubリポジトリ
- オーケストレーター：各プロダクトリポジトリ内で状態を読み、次工程を進めるAIエージェント
- プロトタイプフロー：価値・利用シナリオ・技術成立性を検証するための使い捨て前提の工程
- 本番開発フロー：仕様確定後に品質・レビュー・承認を経てリリースする工程
- 環境オーバーレイ：会社固有ポリシーや環境固有設定を共通マスターに戻さず適用する設定群
- 手動ハンドオフ：ユーザーが機密性を確認し、環境間で最小限の情報を転記する補助手段

## 3. アクターと境界

### アクター

- ユーザー：目的・仕様・本番移行・マージを承認する
- オーケストレーター：工程判定、成果物作成、調査、実装、テスト、レビュー、PR作成を行う
- Codexアダプター：CodexのSkills・指示・起動方法へ変換する
- Copilotアダプター：Copilot instructions・prompt・custom agentへ変換する
- GitHub/CI：Issue、PR、リポジトリ、機械的品質検証を提供する

### 情報境界

共通マスターの配布・更新は、共通マスターから各環境への一方向とする。個人環境と会社環境のオーケストレーターは独立して動作する。会社環境の詳細ログ、テスト結果、会社固有ポリシーは会社環境内に閉じる。

会社環境から共通マスターへのフィードバックは自動連携しない。必要な場合、ユーザーが機密情報を確認・抽象化して、ワークフロー改善用のIssueなどへ手入力する。

## 4. 共通マスター

共通マスターは独立GitHubリポジトリとして管理し、SemVerでリリースする。

```text
workflow-package/
├── workflow/
├── skills/
├── templates/
├── validators/
├── adapters/
│   ├── codex/
│   └── copilot/
├── installer/
├── fixtures/
└── CHANGELOG.md
```

会社環境が共通マスターを読み取れる場合は、指定バージョンを直接導入する。読み取れない場合は、会社内GitHubに読み取り専用ミラーを置く。正本は一つとし、ミラーから共通マスターへ変更を書き戻さない。

## 5. プロダクト側の構成

導入先には`.ai-workflow/`を作成する。

```text
.ai-workflow/
├── config.yml
├── state/
├── requirements/
├── prototypes/
├── plans/
├── reviews/
├── issues/
├── decisions/
├── backlog/
└── handoffs/
```

状態ファイルはMarkdown本文とYAML front matterを組み合わせる。最低限、現在工程、ステータス、承認状態、関連Issue/PR/ADR、ワークフローバージョン、ブロッカー、残課題、最終更新を記録する。

## 6. フロー

### 6.1 プロトタイプフロー

1. アイデア受付
2. 検証目的と成功基準の軽量grilling
3. プロトタイプ作成
4. テスト・評価
5. 本番移行候補と検証結果の整理
6. AIが本番移行可否の根拠を提示
7. ユーザーが本番移行を承認
8. 本番用Issue草案・残課題・初期実装計画を作成
9. ユーザーと本番仕様grillingを実施

プロトタイプコードは原則として本番コードへ自動昇格しない。検証結果、利用シナリオ、採用・却下した案、再利用可能な素材、残課題を本番フローへ引き継ぐ。品質基準を満たすコードの再利用は、ユーザー承認を条件とする。

### 6.2 本番開発フロー

1. 要件grilling
2. `CONTEXT.md`とADRの更新
3. 実装計画の作成
4. 計画レビュー
5. ユーザー承認
6. 実装
7. テスト
8. 自己レビューとPRレビュー
9. PR作成
10. ユーザー承認
11. マージ
12. `CONTEXT.md`、ADR、残課題、状態ファイルの更新

### 6.3 モード

- 自動モード：現在工程を判定し、次の承認ポイントまたはブロッカーまで進める
- 手動アシストモード：ユーザーが個別Skillを呼び出す。成果物、状態、承認条件は自動モードと共通にする

## 7. 権限と停止条件

オーケストレーターは、調査、成果物作成、コード編集、テスト、レビュー、Issue/PR作成を行える。次の操作では必ず停止する。

- 本番仕様の確定
- プロトタイプから本番への移行
- 会社固有ポリシーの変更
- 破壊的操作
- マージ
- ルール衝突、前提矛盾、機密境界違反の可能性

承認要求には、承認対象、変更概要、判断理由、影響、リスク、残課題、承認後の処理を含める。承認記録には承認者、日時、対象バージョン、判断理由、次工程を残す。

## 8. モデル設定とコンテキスト

プロジェクトごとのモデル設定は`.ai-workflow/config.yml`に保存する。環境固有ポリシー、プロジェクト設定、共通推奨値の優先順位は次のとおりとする。

```text
環境固有ポリシー > プロジェクト設定 > 共通推奨値
```

モデルは工程、変更規模、リスク、失敗回数、レビュー難易度に応じて推奨する。標準モデルを低コストに設定し、要件grilling、計画レビュー、セキュリティなど必要な工程だけ強化する。

トークン制限に対応するため、工程ごとに必要な成果物だけを選択し、元文書全体ではなく差分・索引・ハンドオフサマリーを優先する。ハンドオフサマリーには目的、決定事項、根拠、未決事項、関連ファイルを含める。圧縮・分割後も上限を超える場合は停止してユーザーへ通知する。

## 9. GitHubとCI

GitHub CLIを基本とし、必要な操作だけAPIで補助する。オーケストレーターは工程・成果物・承認を管理し、CIはテスト、Lint、Formatter、型チェック、ビルド、その他の機械的品質検証を担当する。

Issue、PR、ADR、実装計画は相互リンクと識別子で紐づける。詳細なテストログは実行環境のGitHub/CIを正本とする。

## 10. 会社環境の機密境界

会社環境では、会社内GitHubと会社内CIを正本とする。テスト詳細・ログ・会社固有ポリシーは会社環境外へ自動送信しない。

個人環境へ情報を戻す必要がある場合は、ユーザーが手動で機密性を確認する。共通マスターが受け取るフィードバックは、一般化された改善要望に限定する。

## 11. 更新

`update`は現在バージョン、更新候補、変更概要、影響範囲、互換性、必要なマイグレーションを提示する。状態・成果物・既存設定を検証し、ユーザー承認後に適用する。既存ファイルは無断で上書きしない。

更新処理は、状態ファイルの互換性確認、必要なマイグレーション、検証、承認、適用、更新記録の保存を順に行う。

## 12. 必須コマンド

- `setup`：プロジェクトを調査し、設定候補を作成して導入する
- `status`：現在工程、承認状態、ブロッカー、残課題を表示する
- `next`：次工程を判定し、承認ポイントまで進める
- `validate`：状態、成果物、リンク、互換性、工程遷移を検証する
- `update`：共通マスターの更新候補を確認し、承認後に更新する

## 13. 受け入れ基準

- fixtureプロジェクトへ指定バージョンを導入できる
- CodexとCopilotの双方で`setup`、`status`、`next`、`validate`が利用できる
- プロトタイプから本番用Issue草案と本番仕様grillingへ情報を引き継げる
- 本番仕様確定、移行、マージでオーケストレーターが停止する
- 承認なしに会社固有ポリシー、破壊的操作、マージを実行しない
- セッションを跨いで状態を読み取り、途中工程から再開できる
- 会社環境の詳細テストログが外部へ自動送信されない
- マスター更新前に互換性・影響・マイグレーションを提示できる
- 既存ファイルを無断上書きせず、衝突時に停止できる
- fixtureを用いた導入、更新、検証、状態遷移の自動テストが通る

## 14. 未解決事項とリスク

- 会社環境から共通マスターを読み取れるかは、実環境で検証する
- Copilot側でカスタムエージェント、プロンプトファイル、指示ファイルをどこまで利用できるか確認する
- Node.jsなどの実行環境が会社端末で利用できるか確認する
- GitHub CLI/APIの認証方式と会社内GitHubのホスト差を確認する
- 会社環境のテスト結果から、手動転記可能な項目を会社ポリシーに合わせて確定する
- Codex/Copilot間で、同一のオーケストレーター指示をどこまで再現できるかfixtureで検証する

## 15. 実装フェーズ

### Phase 1：共通フローの最小縦切り

共通成果物形式、状態ファイル、`setup`、`status`、`validate`、プロトタイプから本番Issue草案までを作る。Codex/Copilot双方のfixtureで検証する。

### Phase 2：本番フロー

要件grilling、`CONTEXT.md`、ADR、実装計画、承認、テスト、PRレビュー、完了後更新を実装する。

### Phase 3：オーケストレーター自動進行

`next`、承認停止、異常停止、実行記録、手動アシストモードを実装する。

### Phase 4：更新と会社環境対応

バージョン更新、互換性検証、マイグレーション、会社内GitHub、Copilotアダプター、機密境界テストを実装する。

## 16. ハンドオフ

本仕様は、Phase 1の実装に着手するためのドラフトである。実装前に会社環境の読み取り可否、Copilot機能、ランタイム、GitHub認証を検証し、未解決事項を更新する。
